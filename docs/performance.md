# Performance and memory budgets

`cargo xtask perf` measures how PdfCraft behaves on large documents and fails when a median
exceeds its budget in [`xtask/baselines/perf.json`](../xtask/baselines/perf.json). It tracks
parity rows `misc.performance-budgets` (P0, M14) and `view.large-document-performance` (M3) and
gives `core.lazy-loading` a baseline to improve on. It is a regression harness on one machine, not
proof that Tier-1 platforms meet a budget.

```sh
cargo xtask perf                      # dev profile, 1 warm-up + 3 measured runs per probe, gates
cargo xtask perf --runs 5             # more samples
cargo xtask perf --report-only        # record numbers, never fail (CI's nightly job)
cargo xtask perf --only text-500      # one scenario (comma-separated list)
cargo xtask perf --no-ui --no-oracle  # engine probe only, skip the Poppler reference
cargo xtask perf --release            # release profile (no budgets recorded yet: report only)
cargo xtask perf --keep               # keep the generated PDFs in <target>/perf/ for manual probing
```

The report is written to `<target>/perf/perf-report.json` (machine, git revision, load average
before/after each scenario, SHA-256 of each generated file, and per metric the median, min, max,
spread and budget).

## What it measures

**Documents.** Generated by `xtask/src/perf.rs` on every run: original synthetic content, no
corpus files and no assets, byte-for-byte deterministic (their SHA-256 is in the report and a unit
test checks determinism). Each has the phrase `quartz zebra final marker` once, on its last page.

| Scenario | Content | File |
|---|---|---|
| `text-500` | 500 Letter pages × 40 Helvetica lines, one Square comment per page (the M3 "500-page document") | 1.7 MB |
| `text-5000` | 5 000 pages of the same kind, to show how costs scale | 16.9 MB |
| `images-24` | 24 pages, each a full-page 1275×1650 RGB Flate image (150 dpi; ~151 MB decoded) | 109 MB |
| `vector-1` | 1 page with 100 000 filled polygons and 10 000 stroked Bézier curves | 2.7 MB |

**Engine probe** (`crates/automation/examples/perf_probe.rs`): the automation tool table that
`pdfcraft-cli run` and MCP use, in a fresh process per run on a fresh copy of the file:
`doc_open` (includes reading the file), `page_render` of page 1 and of the last page at 96 dpi
(PNG encoding included, as an agent receives it), `text_extract` of every page, `text_find`, an
incremental `doc_save` in place after a metadata edit, and a full `doc_save` to a new path. The
probe checks that the saves really were incremental and full, and that find hits the phrase.

**UI probe** (`crates/ui-egui/examples/perf_ui.rs`): the real shell under egui_kittest (no window,
no GPU submission), fresh process per run:

- `open_ms`: `PdfCraftApp::open_bytes`; `first_frame_ms`: the first frame after it;
- `settle_ms`: open + first frame + time until no render has been pending for three frames, i.e.
  the first page is on screen at full quality (the probe fails if no page raster exists then);
- `smooth_scroll`: 300 back-to-back frames scrolling a tenth of a page per frame;
  `jump_scroll`: 200 frames jumping 2.5 pages per frame. Render workers keep running; each frame
  time is the UI thread's own work for that frame. Median, p95, max and frames over 16.7 ms;
- `navigate`: for five far jumps, the time until the target page is settled (median and max);
- the app chooses its panels as for a user: documents with comments open the Comments panel.

**Peak RSS** (`*.peak_rss_mib`): `VmHWM` from `/proc/self/status`, read by the probe itself, so it
is the peak of that one run's process (Linux only; absent elsewhere). Per-phase values are the
peak *so far* (cumulative), which shows which phase raised it.

**Reference** (`oracle.*`, never budgeted): `pdftotext` of the whole file and `pdftoppm` of page 1
at 96 dpi, when Poppler is installed. These include process start-up and file output.

## Noise handling and budgets

- Every probe run is a new process; the first run per scenario is a discarded warm-up.
- Medians over the measured runs are compared with the budget; min, max and spread are reported
  so a noisy run is visible rather than averaged in.
- Budgets are roughly 3–5× the medians measured on a shared, heavily loaded machine (below), with
  absolute floors for millisecond-scale metrics, so ordinary noise never fails but a gross
  regression (a quadratic loop, a cache that stops working, a whole extra copy of the file in
  memory) does. They were set for the **dev** profile, which is what `cargo xtask perf` builds by
  default and what lane worktrees share; there are no release budgets yet.
- UI frame-time p95/max and the `over_16_7ms` counts are reported but not budgeted: on a loaded
  machine they measure the scheduler more than PdfCraft.
- Shared CI runners differ from the measuring machine, so the nightly CI job runs with
  `--report-only` and uploads the report. Gate on a known, quiet machine.

## Measurements (2026-10-12, dev profile)

Three passes of `cargo xtask perf --report-only` (each 1 warm-up + 3 measured runs per probe, so 9
measured runs per metric) on WSL2 Ubuntu 24.04, AMD Ryzen 7 9850X3D (8 cores visible), 12 GiB,
at `e00874e` + this branch. **The machine was shared with up to a dozen other agents' Rust
builds** (load average 6–27 during the passes; the third pass ran at 22–27), so these numbers are
upper bounds for this hardware, not clean figures. "Median" is the median of the three pass
medians; "range" is the fastest and slowest of all nine runs.

| Metric (median, range) | text-500 | text-5000 | images-24 | vector-1 |
|---|---|---|---|---|
| Engine open | 25 ms (22–38) | 322 ms (259–411) | 39 ms (33–77) | 2.4 ms (2–7) |
| Render first page, 96 dpi PNG | 27 ms (21–36) | 31 ms (29–40) | 261 ms (244–343) | 750 ms (703–1041) |
| Extract text, all pages | 579 ms (379–691) | 5.1 s (4.1–6.6) | 3 ms | 68 ms (62–87) |
| Find (whole document, text cached) | 34 ms (17–73) | 207 ms (191–405) | 0.1 ms | 0.1 ms |
| Incremental save | 35 ms (22–69) | 466 ms (330–639) | 104 ms (77–980) | 2.7 ms |
| Full save | 41 ms (34–81) | 512 ms (444–713) | 70 ms (59–83) | 1.8 ms |
| Engine peak RSS | 117 MiB | 988 MiB | 354 MiB (350–378) | 147 MiB |
| UI time to first page on screen (`settle_ms`) | 53 ms (34–98) | 693 ms (599–891) | 44 ms (40–74) | 800 ms (675–900) |
| UI smooth scroll, median frame | 8.1 ms (7.2–12.0) | 198 ms (154–276) | 0.1 ms | 0.2 ms |
| UI smooth scroll, p95 frame | 16.7 ms (13.4–23.7) | 294 ms (204–539) | 0.4 ms | 0.3 ms |
| UI jump scroll (2.5 pages/frame), median frame | 16.1 ms (10.8–20.1) | 208 ms (170–226) | 0.1 ms | 0.2 ms |
| UI navigate to a far page, settled | 40 ms (28–62) | 655 ms (489–766) | 49 ms (39–72) | 0.2 ms |
| UI peak RSS | 161 MiB (147–166) | 428 MiB (415–441) | 320 MiB (306–323) | 177 MiB |
| Reference: `pdftotext` whole file | 152 ms | 1.4 s | 8 ms | 179 ms |
| Reference: `pdftoppm` page 1, 96 dpi | 109 ms | 115 ms | 458 ms | 3.3 s |

Spread between runs of the same metric was typically 20–70 % for timings (up to 2–9× for
single-digit-millisecond phases and for one 980 ms incremental save outlier on `images-24`) and
≤ 12 % for peak RSS. This is why the gate uses medians and budgets several times the median.

What the numbers support:

- **M3 "60 fps on a 500-page document":** on `text-500`, the UI thread's own work per frame while
  scrolling continuously has a median of 8.1 ms and a p95 of about 16.7 ms on this loaded machine
  (dev profile, which is slower than release); 6–20 of 300 frames per run exceeded 16.7 ms. Jumping
  2.5 pages per frame is around 16 ms median. Frames here exclude GPU submission and presentation
  (kittest does not paint), so this is evidence about UI work, not about delivered frames on a real
  display.
- Rendering stays off the UI thread: image-heavy and vector-heavy pages render in 0.25–0.8 s on
  workers while scroll frames stay under a millisecond.
- PdfCraft renders the vector page ~4× faster and the image page ~1.7× faster than `pdftoppm`
  (whose time includes process start and PNG writing), and extracts text ~3–4× slower than
  `pdftotext` on the text documents (reference only; different work and output format).

## Defects found

1. **Comments panel cost grows linearly with the comment count, every frame.** Documents with
   comments open with the Comments panel (as Acrobat does). With 5 000 comments the median frame
   is ~200 ms (≈5 fps) while scrolling; with the panel closed the same document scrolls at
   a 0.6 ms median frame (one run each, 2026-10-12: 142 ms with the panel, 0.64 ms without; 13 ms vs 434 ms to settle a far page). Cause (`crates/ui-egui/src/comments_panel.rs`, `show`): every frame it filters
   and lays out every card (no row virtualization), counts each page group's comments with a scan of
   all annotations (O(pages × annotations)), and calls `replies_of` (a scan of all annotations)
   up to three times per root comment when comments have names, which is quadratic for named
   comments. On `text-500` (500 comments) the panel is most of the 8 ms frame.
2. **Unbounded text cache in the automation session (fixed 2026-10-12, wp/hardening).**
   `text_extract`/`text_find` cached every page's `PageText` (with glyph geometry) for the life of
   the document: extracting 5 000 pages raised peak RSS from ~110 MiB to ~873 MiB (≈155 KiB per
   40-line page) and it was never released. The cache (`crates/automation/src/text_cache.rs`) is
   now bounded at 96 MiB of estimated heap across all documents, evicting the least recently used
   pages and dropping a document's pages when its working bytes change or it closes; whole-document
   tools (`text_extract`, `text_find`, `redact_mark`) stream pages from parallel workers through
   a bounded channel instead of holding them all. Tool results are unchanged
   (`text_cache::tests::bounded_cache_keeps_tool_results_identical` compares a one-byte budget with
   an unbounded one, including after an edit). Alongside it, a geometry-free search index
   (`SearchText`: the exact chars page search runs on, case-folded and original, ~2 bytes per
   glyph each) has its own 32 MiB LRU budget and the same invalidation. `text_find` and
   `redact_mark` skip pages the index proves match-free, so only matching pages need their
   geometry re-extracted (`PageText::search_text` + `find_in_chars` in `pdfcraft-render`; the
   render test `search_text_agrees_with_page_search` and the automation test, which also runs
   with only the index enabled, check the results are identical). One dev-profile `perf_probe`
   run on `text-5000` (logs `~/artcraft/logs/wp-hardening/perf-report-{before,index}.json`):
   peak RSS after extraction 874 → 369 MiB, whole run 989 → 484 MiB; extraction 2.3 → 2.8 s;
   `find` after `extract` 167 → 49 ms (geometry-only cache without the index: 2.4 s). `text-500`
   is unchanged within noise (find 17 ms, peak 120 MiB). The original find budget (830 ms)
   stands; the `text-5000` RSS budget is now 610 MiB. Most of the remaining extraction peak is
   the eight extraction workers each parsing the document.
3. **Whole file in memory** (known, `core.lazy-loading`): `doc_open` reads the entire file and the
   engine keeps it (`crates/cos/src/lib.rs`: no `ByteSource` yet). `images-24` (109 MB) opens at
   ~120 MiB RSS and peaks at ~354 MiB after rendering, extraction and two saves.
4. **Text-5000 opens in ~0.3 s and saves in ~0.5 s** — linear in object count, acceptable today,
   recorded so it cannot regress unnoticed.

## Not covered

- Release builds (`--release` works but no budgets are recorded), Windows, macOS, FreeBSD and the
  web build. `misc.performance-budgets` stays `partial` until Tier-1 platforms are measured.
- GPU upload/present time, real input latency, and multi-gigabyte files (would need
  `core.lazy-loading` first; generating them would also cost scarce disk here).
- Deep or unbalanced page trees, fonts with large embedded programs, and encrypted files.
