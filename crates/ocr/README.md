# Text recognition

`pdfcraft-ocr` runs the bundled `ocrs` model and writes invisible searchable text. `engine::ocr` renders PDF pages, bounds the input, and binds each recognition draft to the source document version. The UI reviews words before applying by default. The original page image stays intact.

The validated recognition language is **English**. The bundled recognition model has an ASCII output alphabet. Editing the language list or supplying a different alphabet does not train the model to recognize accented letters or other scripts. Corrected searchable words may contain WinAnsi characters, including Latin accents; unsupported characters are rejected instead of becoming question marks. The recognition API does not expose calibrated word confidence, so the review lists every word rather than inventing “suspect” scores.

Fetch the existing, manifest-pinned models with `cargo xtask models`, or set `PDFCRAFT_MODELS` to a directory containing both `.rten` files. Desktop packages ship both models, their license texts and attribution. Tests that print `skipped: OCR models not installed` are **not** evidence that recognition ran. Set `PDFCRAFT_MODELS_REQUIRED=1` (Linux CI does, after `cargo xtask models`) to turn that skip into a failure (`Models::required_for_tests`), so a passing run means the actual models ran.

## Engines

Recognition engines are pluggable (`src/engines.rs`). An `OcrEngine` has an id, a name, `info` (available, version, languages as ISO 639-1 codes, whether it is an external program, and where it was found or why it can't run), `prepare(language)` (called once before a job's pages are read, so a missing engine fails the job, not every page) and `recognize(pixels, width, height, language)`, returning the same `Line`s/`Word`s as the built-in engine. A `Registry` holds them; the default one has:

- `ocrs` (default): the built-in, pure-Rust engine with the pinned models, loaded once per process (`OcrsEngine::shared`). English only.
- `tesseract` (optional, `src/tesseract.rs`): runs an **installed** `tesseract` program as a separate process. It is never linked, bundled or shipped. The program is the configured path (`Session::set_tesseract_path`), else `$PDFCRAFT_TESSERACT`, else `tesseract` on `PATH`; without it the engine is listed as unavailable with the reason. The page goes to its standard input as a binary PGM/PPM (RGBA composited over white), and its TSV output (`stdin stdout -l <lang> --psm 3 tsv`) is parsed by `parse_tsv`: only word rows; malformed rows, boxes outside the image, empty or overlong words and words with characters the searchable-text font can't encode (after spelling out ligatures) are left out; confidence 0–100 becomes 0–1, so editable output's `min_confidence` applies. Each recognition has a 120 s limit and a 32 MiB output cap (64 KiB of standard error); version and language probes 10 s; more than 200,000 words or 16 MiB of text on a page is refused. Languages are the installed trained data among `KNOWN_LANGUAGES` (13 Latin-script languages the WinAnsi text layer can encode). The web build can't start programs, so there it is always unavailable (the process code is compiled out on wasm).

The engine `Session` keeps the registry and the selected engine (`ocr_engines`, `set_ocr_engine`, `register_ocr_engine`); `OcrSettings::engine` names another for one job, and `Session::ocr_engine_for` resolves and checks it (registered, reads the language) before any page is rendered. Every entry point uses it: `recognize_text`, `OcrJob::run_selected` (review drafts, editable output, the dialog's worker), `recognize_file` (multiple files), camera-then-recognize and Make Accessible. Automation: `ocr_engines_list`, `ocr_engine_set`, and `engine` on `ocr_recognize`, `ocr_prepare` and `ocr_recognize_files`. The Tesseract program path is deliberately not settable through tools (only the environment or the Session API), so an agent can't make PdfCraft run an arbitrary executable.

Tests: `src/engines.rs` (registration, ids, defaults), `src/tesseract.rs` (TSV parsing with synthetic, malformed and huge output; PNM encoding; a missing program; on Unix a stand-in shell program with Tesseract's command line for probing, stdin/stdout, failure, timeout and output-cap handling; a real run that skips unless Tesseract with English data is installed), `crates/engine/tests/ocr_engines.rs` and `crates/automation/tests/ocr_engines.rs` (fake registered engines through every entry point and tool). CI does not need Tesseract.

## Permissions

Recognition copies a document's content (the recognized words) and adds a text layer, so it needs both the copy permission used by text extraction (`Document::allows_copying`) and the modification permission used by other content edits (`Document::allows_modification`). Opening a restricted encrypted file with its permissions (owner) password lifts both. `Session::ocr_authority` checks them before a job is built, so nothing is rendered and no model runs for a restricted document. `validate_ocr_review` checks them again, against the document as it is now, whenever a draft is shown, corrected or applied, before checking the revision. Automation discards a draft that fails these checks without returning its words; the UI discards it without showing them.

## Review workflow

- `Session::ocr_job_checked` validates the language, resolution, selected pages and permissions before rendering or loading models.
- `OcrJob::run` produces an `OcrReview`. It never mutates the document. Returning `false` from any progress callback cancels the entire draft, including completed pages. Inference currently finishes before cancellation is observed; it is not interruptible inside a model call.
- `OcrReview::correct` changes a word or omits it when empty, preserving its placement. Corrections have per-word, per-page and per-draft limits.
- `Session::apply_ocr_review` rejects a closed or changed document, including edits followed by undo. Accepted results create one undoable edit. Save remains incremental.
- The lower-level `apply_ocr`/`Edit::AddOcrText` APIs also validate public word geometry and text before generating PDF syntax. The invisible layer uses `q`/`Q` so its text rendering mode cannot affect later content.

Recognition images are limited to 40 million pixels and 16,384 pixels per side. Resolution must be finite and 72–600 dpi. Packed gray/RGB/RGBA lengths are checked before allocating conversions; RGBA input is composited over white for inference. A job accepts at most one million words / 64 MiB of text, with additional per-page and per-word bounds. Oversized pages are reported as skipped with a reason; they are not silently shrunk. Backend panics are contained and produce no committed text.

## Headless control

`ocr_prepare` creates a draft; `ocr_review` returns words, geometry and skip reasons, or an error (discarding the draft) when the document changed, closed or no longer allows copying and changes; `ocr_correct` changes one 1-based page/word; `ocr_apply` commits once; `ocr_cancel` discards it. At most eight drafts, two million recognized words and 128 MiB of text may be retained together in an automation session. Batch recognition (`ocr_recognize_files`, the UI's multiple-files command) cannot be canceled yet and reads each input file whole. Closing a document releases its draft. Existing `ocr_recognize` remains a synchronous recognize-and-apply operation, and batch recognition continues to write searchable copies.

## Orientation and deskew

`OcrSettings::auto_rotate` and `OcrSettings::deskew` (tool arguments `auto_rotate`/`deskew`, dialog "Detect page rotation"/"Deskew pages") are **off by default**. When on, `orient::correct` finds the text direction of the rendered page, builds a corrected gray copy for recognition, and returns the affine map from that copy back to the rendered pixels; the engine composes it with the page's view-to-user mapping, so each word's box becomes a (possibly rotated) parallelogram over the visible word. The page image and `/Rotate` are never changed (exact mode). Each recognized page reports `orientation` (`rotation` 0/90/180/270° counterclockwise, `skew` in degrees).

The method is original code, documented in `src/orient.rs`: Otsu-binarized projection profiles on a copy of at most 1000 px per side find the text-line axis and skew within ±15°; the two readings of that axis (or all four when the axis is ambiguous) are recognized at most 1600 px per side and compared by a dictionary-free plausibility score (word-shaped letters and digits count, implausible words subtract). Upright is kept unless another reading scores clearly higher, and nothing is turned when no reading is plausible. This costs up to four extra recognitions of a reduced page.

Measured with the pinned models (`crates/automation/tests/ocr_orient.rs`, one original 4-line, 30-word Helvetica page rendered at 150 dpi): orientation detected correctly at 0/90/180/270° and 93/173/263°; skew within 0.1° at ±3/±7°; 30/30 words except 29/30 at ±7°, and every recognized word located on its visible word. Without the options, 90/180/270° pages yielded 0 correct words. These are observations on synthetic fixtures, not general accuracy claims.

## Despeckle

`OcrSettings::despeckle` (tool argument `despeckle: off|low|medium|high`, plus `despeckle_light` and `despeckle_median`; default off) removes isolated specks from a gray copy of the rendered page before orientation detection and recognition (`pdfcraft_optimize::despeckle`, sized by the rendered resolution; specks near text-sized ink are kept so punctuation survives). Each read page reports what was removed (`despeckle`). In Exact mode the page image is unchanged; with Searchable Image (`straighten`) the recognized pages' images are despeckled too (`Edit::DespecklePageImages`, before downsampling) in the same undo step. `Session::despeckle_scans` / `scan_despeckle` does the same as a standalone undoable edit. No dialog option yet; measured on synthetic fixtures only.

## Background removal

`OcrSettings::background` (tool argument `background: off|low|medium|high`, plus `background_white_point`; default off) whitens the paper background of a gray copy of the rendered page before despeckling, orientation detection and recognition (`pdfcraft_optimize::background`). Each read page reports the paper level, white point and pixels whitened (`background`). In Exact mode the page image is unchanged; with Searchable Image (`straighten`) the recognized pages' images are whitened too (`Edit::RemovePageImageBackgrounds`, before despeckling and downsampling) in the same undo step. `Session::remove_scan_backgrounds` / `scan_remove_background` does the same as a standalone undoable edit.

## Editable Text and Images

`OcrSettings::editable` (tool argument `output: editable`, plus `min_confidence`, default 0.5; not with `straighten`) replaces the recognized text with real, visible text and keeps the page image as the background with the text areas cleaned out. The analysis and PDF syntax are original code in `src/editable.rs` (module docs): words are grouped into lines; each line's baseline, size (per candidate face, from the recognized letters' ascender/cap/x-height), colour (darkest half of the ink) and paper colour are measured in the recognition image; a standard face — Helvetica, Times-Roman or Courier, regular or bold — is chosen by the words' width fit, stroke contrast and stem weight, and the line is written with `Tz` fitting the words' widths and `TJ` offsets putting each word where it was read. The engine maps lines to user space (`EditableLayout` on each `OcrPage`) and applies them as one `Edit::AddEditableOcrText`: the converted words are filled with the local paper colour in the page images (`pdfcraft_optimize::inpaint_page_image_regions`), areas no image covers are painted with paper colour instead, and the text is stamped on top. Words the backend scores below `min_confidence` — or, since the bundled `ocrs` engine reports no confidence (`Word::confidence` is `None`), words failing the dictionary-free word-shape test — stay as image with invisible text in their place in the line, as do undrawable words and lines without measurable ink. Corrections change the visible text; a word emptied by a correction keeps its ink. With `background`/`despeckle` the page images are cleaned too, in the same step. Measured only on synthetic fixtures with a stand-in recognizer (`crates/engine/tests/ocr_editable.rs`); see the parity notes for what is missing.

## Run OCR when exporting

Export to Word, HTML, RTF, Excel, PowerPoint (editable mode) and text recognizes scans first, as the viewer's export setting does. `engine::export_ocr` holds it: `ExportOcr { mode, language }` with `ExportOcrMode::Auto` (default: pages that draw an image and have no text, only when the selected engine can run and reads the language), `On` (every exported page without text) or `Off`. `Session::with_export_ocr(id, pages, options, export)` opens a temporary copy of the document's working file (unsaved edits included, same password), recognizes the pages that need it as Searchable Image (Exact) with the usual `ocr_job_checked` validation and permission checks, and hands that copy to the exporter; the document, its undo history and dirty state never change. It reads with the session's selected engine (`Session::ocr_engine_for`; the copy gets the same engine), and `language` is any `KNOWN_LANGUAGES` code that engine reads. When the engine can't run (no models, Tesseract not installed) or doesn't read the language, or when the document's permissions forbid recognition, `Auto` exports as is and `ExportOcrReport::not_run` says why, while `On` fails before anything is written. `with_export_ocr_using` takes the recognizer explicitly instead (the engine tests use a stand-in; built-in languages only). Tools: `ocr` (auto/on/off) and `ocr_language` on `doc_export_office`, `doc_export_pptx` and `doc_export_text`, which return the report as `ocr`. Because the recognized text is the invisible layer, the exports carry the recognized paragraphs next to the scan image itself; fonts and styles are not recovered from the scan.

## Remaining OCR work

This workflow does not complete PDF OCR parity. Image cleanup beyond despeckle and global background removal (descreen, halo and edge-shadow removal, uneven-lighting correction), calibrated confidence from the bundled model, correction of an already-saved OCR layer, arbitrary Unicode text layers, editable-text fidelity beyond the standard fonts (glyph matching, embedded fonts, italic, paragraph reflow), multilingual recognition, scanner capture and MRC compression remain separate tasks. Existing PDF `/Rotate` and crop geometry are respected when placing recognized words; that is not automatic orientation detection.

For multilingual work, both the recognition model and searchable-text font/encoding must support the target script. An independently licensed model with verified trained alphabets, reproducible original fixtures and a compatible Rust/WASM runtime is required. An installed Tesseract can now be used as an optional external engine (see Engines) for the Latin-script languages its data covers, but that does not help the web build or scripts the text layer can't encode. Paddle-family models require model-specific license and runtime compatibility verification. No new model or backend is bundled by this change.

## Tests

- `crates/ocr/src/orient.rs`: exact quarter turns, the documented back-mapping, skew estimation on synthetic lines, candidate choice, blank/dark/hostile images and the plausibility score.
- `crates/automation/tests/ocr_orient.rs`: real-model `ocr_recognize` with `auto_rotate`/`deskew` on fixtures turned 0/90/180/270°, skewed ±3/±7° and combined, asserting detected orientation, recognized words, reading order, searchable text over the visible words after save, and unchanged page pixels; options default off and reject non-boolean values.
- `crates/ocr/src/lib.rs`: hostile dimensions/channel lengths, transparent input, word encoding/geometry and balanced invisible text state.
- `crates/engine/tests/ocr_review.rs`: all cancellation boundaries, stale authority, correction/save/reopen pixel equality, one undo, rotated page mapping, oversized pages and panic containment using a deterministic test recognizer; encrypted fixtures made with the engine's own Protect (copy denied, modify denied, both, owner password, a draft whose permissions or revision later change) asserting refusal before the counting recognizer runs and no data or history change.
- `crates/automation/tests/ocr_review.rs`: real-model review/correct/cancel/apply/save/reopen, unsupported corrections, stale drafts and output root confinement; the same encrypted cases through `doc_protect`/`doc_save` for every OCR tool, including batch recognition, owner password and a later security change.
- `crates/engine/tests/export_ocr.rs`: Run OCR on export with a stand-in recognizer: pages chosen per mode and per exported page range, the export reading the recognized copy while the document's bytes and history stay as they were, missing models, an unsupported language, a document that forbids changes, and a registered engine selected for the export (its language read, others refused).
- `crates/automation/tests/export_ocr.rs`: real-model export of an original 200 dpi synthetic scan to .docx, .html, .rtf, .xlsx, .pptx and .txt with `ocr` auto/on (at least 80% of the words) and off (none of them), a mixed text/scan/blank document, argument validation, and the no-models behaviour.
- `crates/ui-egui/tests/ocr.rs`: actual recognition in the shell, review/apply, corrected word navigation, Escape cancellation and stale-document refusal.
